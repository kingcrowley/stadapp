# Slice 1.1 — Block list — Design

**Date:** 2026-11-17
**Branch:** `phase/1-slice1-block-list`
**Status:** built, in review (PR #2). Revised after an independent plan review; see "Review changes" below.

## Problem

Stad can't block anything until it knows *what* to block. This slice lets the user choose apps from the ones installed on the phone, and keeps that choice across restarts. Nothing is blocked yet: that is slice 1.2.

## Goals

1. A searchable app picker listing the phone's launchable apps (icon, name, checkbox).
2. The selection persists on the device and survives killing and reopening Stad.
3. Apps that must never be blocked (Stad, every home-screen app, the Phone and SMS apps, Settings, the system UI) can't be selected.
4. The home screen shows how many apps are blocked and opens the picker.
5. The "read-only while locked" rule exists in `core/` with tests, ready for 1.2 to switch on.

## Non-goals

- Blocking, the Accessibility service, the block screen (1.2).
- Persisting the lock state (2.1). In 1.1 the lock is always `Unlocked` in memory.
- Categories, schedules, multiple block lists or profiles.
- Work-profile apps (the picker shows the main profile only). `TODO(slice1.1-work-profile)`.

## User flow

1. Home: "Unlocked · 0 apps blocked" and a **Choose apps** button.
2. Picker: search box on top; list sorted A–Z by app name; ticking or unticking saves at once (no Save button). Protected apps appear greyed out with "Can't be blocked" so it's clear why.
3. Back to home: "Unlocked · 3 apps blocked".
4. While locked (from 1.2 on), the picker opens read-only with a banner "Unlock with your tag to change this list."

## Design

### core/ (pure Kotlin, JVM-tested)

| Type | Responsibility |
|------|----------------|
| `AppEntry(packageName, label)` | One launchable app, as the picker sees it |
| `BlockList` (value class over `Set<String>`) | `contains`, `size`, `toggled(pkg)` |
| `BlockListRules` | `canEdit(lockState)`; `isBlockable(pkg, protected)`; `setBlocked(list, pkg, blocked, lockState, protected)` returns the list unchanged when locked, or when blocking a protected package; `ALWAYS_PROTECTED` (Stad, `com.android.systemui`, `android`); `sanitize(saved, isInstalled)` drops only confirmed-uninstalled packages; `shouldPersistSanitized(...)` (never while locked, never when the app query came back empty); `effective(list, protected)` and `blockedCount` apply protection on read; `pickerRows(apps, list, protected, lockState, query)` filters (case- and accent-insensitive, name or package), sorts by name with package tie-break, and marks rows checked / protected / enabled |
| `PickerRow` | One picker row: app, checked, protected, enabled |

### data/

- `BlockListRepository` interface: `val blockList: Flow<BlockList>`, `suspend fun update(transform)`. Every change goes through one atomic DataStore `edit {}`, so a toggle and a clean-up can't overwrite each other.
- `DataStoreBlockListRepository`: one app-wide Preferences DataStore (`Context.stadSettings`, file `stad_settings`), key `blocked_packages` (string set). Corrupt file or read error → empty list, never a crash.

### service/ (Android, thin)

- `InstalledApps`: launcher activities → `List<AppEntry>` (one per package, labelled with the app's own label), on `Dispatchers.IO`. `isInstalled(pkg)` uses `getApplicationInfo`, so an app whose launcher entry is briefly disabled, or an archived app, isn't treated as uninstalled.
- `AppIcons`: 48dp bitmaps, loaded per visible row on IO, held in a small `LruCache`.
- `ProtectedPackages`: `ALWAYS_PROTECTED`, every `CATEGORY_HOME` app (not just the default, which resolves to the system chooser when none is set), the default dialer and the `ACTION_DIAL` handler, the default SMS app, the Settings app and `com.android.settings`. Each lookup is independent, so one null doesn't drop the rest. Re-read every time Stad comes to the foreground (`onStart`).
- Manifest: `<queries>` for LAUNCHER, HOME, DIAL, SENDTO (smsto) and `android.settings.SETTINGS`. **No `QUERY_ALL_PACKAGES`** (Play-restricted, see `06_PLAY_POLICY.md`).
- Backup: `dataExtractionRules` excludes everything from cloud backup and device-to-device transfer (`allowBackup=false` alone doesn't cover transfer on Android 12+).

### ui/

- `BlockListViewModel` combines the stored list, installed apps, protected packages, lock state and search query into `BlockListUiState`. All decisions are `BlockListRules` calls; the ViewModel only gathers facts.
- On every `onStart` it re-reads apps and protected packages, then runs `sanitize` inside one `update`, writing back only when `shouldPersistSanitized` says so.
- Screens: `HomeScreen` (count + Choose apps), `AppPickerScreen` (search + `LazyColumn`).
- Navigation: two screens, so a simple screen state in `MainActivity` with `BackHandler`. Move to navigation-compose when a third screen arrives (1.3, pair tag). `TODO(slice1.3-navigation)`.

### New dependencies

| Library | Why |
|---------|-----|
| `androidx.datastore:datastore-preferences` | Persist the list (agreed in the architecture doc) |
| `androidx.lifecycle:lifecycle-runtime-compose` | `collectAsStateWithLifecycle` |
| `org.jetbrains.kotlinx:kotlinx-coroutines-test` (test) | DataStore repository tests on the JVM |

All three are Google/JetBrains open-source, no Play Services, so F-Droid is unaffected.

## Edge cases

- **App uninstalled after being picked:** dropped by `sanitize` next time Stad comes to the foreground (unless locked).
- **A picked app becomes a home app or the default SMS app:** it stays stored but stops counting and won't be blocked. It's never deleted from storage, so changing a system default can't be used to edit the list while locked.
- **App query fails or returns nothing:** no clean-up runs, so the list can't be wiped by a bad read.
- **App with no label / duplicate labels:** fall back to package name; sort ties broken by package name.
- **Hundreds of apps:** list is lazy; icons load per visible row.

## Play policy

The block list is the user's own setting, stored only on the device. Listing apps uses a `<queries>` launcher intent, not `QUERY_ALL_PACKAGES`. No new permissions. `06_PLAY_POLICY.md` already covers this; the slice ticks it off.

## Acceptance

- CI green: build, unit tests, lint.
- 27 new JVM tests: `BlockListRules` (19), `BlockList` (3), `DataStoreBlockListRepository` on a temp file (5). 32 in total with `LockStateTest`.
- On David's phone: pick 3 apps → Home says 3 → swipe Stad away, reopen → still 3 and the same apps ticked. Search finds an app by part of its name. Phone, Messages, Settings, the launcher and Stad show as "Can't be blocked". Uninstall a picked app → count drops by one.

## Review changes

An independent Android review of the first draft (CodeRabbit was rate-limited) led to these changes:

| Finding | Change |
|---------|--------|
| Writing "now protected" drops back to storage would let a locked user edit the list by changing a system default | Protection applies on read (`effective`); `sanitize` drops only uninstalled apps; no write-back while locked |
| A failed or empty app query could wipe the list | Skip clean-up when the query returns nothing; "uninstalled" means `getApplicationInfo` fails |
| `<queries>` only covered LAUNCHER, so HOME/dialer/Settings lookups could silently return nothing on API 30+ | Added HOME, DIAL, SENDTO and SETTINGS; protect every home app |
| Protected set short of the "never block emergency" rule | Added default SMS app and a fixed floor in core (Stad, system UI, framework). OEM emergency app: `TODO(slice1.2-emergency-apps)` |
| Clean-up computed from a snapshot could overwrite a toggle | Single atomic `update { }`; no `replace` |
| DataStore instance and test setup | One app-wide instance; tests cancel the first scope before reopening the file |
| Write-back and count logic untested in the ViewModel | Moved to core (`shouldPersistSanitized`, `blockedCount`) with tests |
| Changes while Stad is open were missed | Re-read on every `onStart` |
| Labels, icons, backup | App label not activity label; 48dp cached bitmaps; `dataExtractionRules` |

Kept as is: Play Store and similar apps stay blockable (they can't disable the blocker; self-protection is slice 2.2), simple screen state for two screens, no new permissions.
