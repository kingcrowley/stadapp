# Slice 2.2 — Escape log — Design

**Date:** 2026-11-21
**Branch:** `phase/2-slice2-escape-log` (cut from `phase/2-slice1-lock-survives`; rebased onto `main` once 1.3 and 2.1 merge)
**Status:** revised after an independent review (see "Review changes")

## Why this replaces "Close the escape routes"

The roadmap's 2.2 planned to block uninstalling Stad, turning off its Accessibility service, and reaching its App info screen while locked. Google Play forbids all three for an app like Stad:

- **Accessibility API** (Play Console Help, "Permissions and APIs that Access Sensitive Information"): it "cannot be used to: Change user settings without their permission or prevent the ability for users to disable or uninstall any app or service, unless authorized by a parent or guardian through a parental control app or by authorized administrators through enterprise management software". Stad is neither.
- **Malware policy**, ransomware: "Leveraging device policy manager features and blocking removal by the user"; "Don't use device admin features to block uninstallation."
- **Malware policy**, elevated privilege abuse: "Apps that abuse features to prevent them from being uninstalled or stopped."

Doing it anyway risks Play rejecting Stad or terminating the developer account. So in the Play build, Stad stays easy to turn off and remove. What it can do is make turning it off while locked **visible**: an honest record you see the next time you open Stad. A strict F-Droid-only build that closes the routes is a later slice (`TODO(slice2.x-strict-fdroid)`, decided 2026-11-21). F-Droid has no such policy, though Android itself still lets safe mode beat it.

## Goals

1. When blocking stops while Stad is locked (the Accessibility service is turned off, or Stad is stopped), Stad records when it stopped and when it came back.
2. Home shows the record: up to 5 recent entries, e.g. "Today 14:02 – 14:20 (18 min)", and how many times in the last 7 days.
3. The record is plain and non-judgemental. It stays on the phone, and can be cleared only while unlocked.
4. Nothing in the Play build prevents disabling, stopping or uninstalling Stad.

User-facing text says "blocking history" and "Blocking was off while locked", never "escape" or "tamper". Internally the slice is still "escape log".

## Non-goals

- Blocking uninstall, the Accessibility switch, App info or Force stop (Play policy; see above).
- Recording what Stad can't see: an uninstall or clearing Stad's storage (both wipe the record with the lock), safe-mode boots (no app code runs; `TODO(slice2.x-safe-mode-gap)`), services suppressed by UiAutomation (adb, developer use), and a work-profile copy of Stad (its own storage).
- Sharing the record, or any network use.

## Behaviour

### How Android stops the service (verified in the review against AOSP `AccessibilityManagerService`)

| Cause | Callbacks in Stad | `ENABLED_ACCESSIBILITY_SERVICES` afterwards |
|-------|-------------------|----------------------------------------------|
| User turns it off in Settings | `onUnbind`, then `onDestroy` (the setting is written first) | Stad not listed |
| Force-stop | None (process killed) | Stad not listed |
| Shutdown / reboot | Usually none (process killed) | Still listed |
| Update of Stad | None (process killed, rebound) | Still listed |
| Crash | None (rebound) | Still listed |
| User switch | `onUnbind`, `onDestroy` | Still listed |

So **the setting tells the cases apart**: an off period exists only when the setting no longer lists Stad while locked, or when the service was killed and came back without Android rebinding it straight away. No shutdown broadcast or timing heuristics: `ACTION_SHUTDOWN` reaches registered receivers only, since API 28.

### Off-period transitions

All through one pure `EscapeTracker`, each applied in **one atomic DataStore edit**. Stored: `off_since` (+ `off_since_approx`), `last_alive`, `locked_at`, `service_connected`, `connected_boot` (wall-clock boot start), and the log.

| Moment | Where | Transition |
|--------|-------|-----------|
| Service stops while locked **and the setting no longer lists Stad** | `onUnbind` (and `onDestroy` if `onUnbind` didn't run); idempotent | `off_since = now` (exact; replaces an approximate one) |
| Service stops, setting still lists Stad (shutdown, user switch) | same | nothing; `service_connected = false` |
| Locked, setting off, no `off_since` (force-stop: nothing ran) | Home `onStart`, `BootReceiver`, tag tap | `off_since = max(last_alive, locked_at)`, approximate |
| Service connects while locked, `off_since` set | `onServiceConnected` | entry `(off_since, now)`; clear |
| Service connects while locked, no `off_since`, but `service_connected` is still true from the **same boot** and Stad wasn't updated since (`lastUpdateTime < last_alive`) | `onServiceConnected` | it was killed and re-enabled without Stad opening (force-stop, then straight back to Settings): entry `(max(last_alive, locked_at), now)`, approximate, if over 60 s (crash restarts are quicker) |
| Unlocked by tag with `off_since` set (or found off at that tap) | inside `TagRepository.tap`'s edit | found-off if needed, then entry ending now, `endedBy = Unlock` |
| Locked by tag | inside `TagRepository.tap`'s edit | `locked_at = now` |

- `last_alive`: written on connect and at most every 15 minutes on window events while locked. Event-driven: no timers or wake-ups.
- `locked_at` caps an approximate start, so a stale `last_alive` from an earlier lock can't stretch an entry back by days.
- User-off periods of any length are kept; only toggles under 5 s are dropped (a double toggle).
- **Teardown writes.** The service's coroutine scope is cancelled in `onDestroy`, and a destroyed service's process can die at once. So the stop write runs synchronously in `onUnbind`: `runBlocking { withTimeoutOrNull(2 s) { repository.onServiceStopped(...) } }`. DataStore does its I/O on its own dispatcher, and a Preferences write takes tens of ms.
- Clock changes: durations clamp at 0, and entries keep insertion order. It's a personal record, not evidence.

### Home

Under the service card, when the log has entries in the last 7 days:

> **While locked, blocking was off 2 times in the last 7 days.**
> Today 14:02 – 14:20 (18 min)
> Tuesday, stopped some time after 09:10, back at 09:45 (start not known exactly)

- Up to 5 entries.
- An approximate entry shows no firm duration.
- **Clear** appears only while unlocked. The product rule still holds: nothing about blocking changes while locked, and clearing the record counts.

### Data

`EscapeLog`: up to 50 entries `{start, end, startApprox, endedBy: ServiceBack | Unlock}`, oldest dropped. Stored in the shared DataStore as one versioned string (`escape_log`); a corrupt or unknown-version value reads as empty. Times are wall-clock (`System.currentTimeMillis`), since the record must survive reboots.

Pure core:
- `EscapeTracker`: `onServiceStopped(settingOn)`, `onServiceConnected(sameBoot, updatedSince)`, `onFoundOff`, `onLocked`, `onUnlocked`. Each takes the stored state and `now`, and returns the new state plus an optional entry.
- `EscapeLog`: `add`, `recent(now, days)`, `summary`, `encode`, `decode`.

## Play policy

No new permissions. Data stays on the phone, so Data safety stays "No data collected"; `06_PLAY_POLICY.md` lists the on/off times among stored settings, changes the Device admin row to "Not used (Play policy; see 2.2)", and gains a row: "Stad never prevents disabling, stopping or uninstalling itself; while locked it only records when blocking was off, on the device". The prominent disclosure gains one sentence: "If you turn this off while locked, Stad notes when, so you can see it later."

## Acceptance

- CI green. JVM tests:
  - `EscapeTracker`: each transition; setting still on → no record; double stop is idempotent; approximate start replaced by exact; approximate start capped by `locked_at`; found-off plus unlock in one tap; killed-then-reconnected in the same boot vs after a reboot or update; sub-5 s toggle dropped; clock going backwards.
  - `EscapeLog`: cap drops the oldest; 7-day boundary; encode/decode round-trip; corrupt and unknown-version input.
  - `EscapeRepository`, `TagRepository`: on a real file DataStore, proving each transition is one edit.
- On the phone, locked with Instagram blocked:
  1. Turn the service off in settings, wait, turn it on → Home: "blocking was off" with the right times.
  2. Force-stop Stad, wait, open Stad, turn on → entry marked "about", starting no later than the last time blocking was seen working.
  3. Force-stop, then turn Stad back on straight from Accessibility settings without opening Stad → entry recorded.
  4. Force-stop, then unlock with the tag without opening Stad → entry ending at the unlock.
  5. Reboot, update, and switching to a guest user and back → no entry.
  6. Quick off/on toggles → one entry each (a double toggle under 5 s doesn't count).
  7. Locking while the service is already off → the entry starts at the lock, not earlier.
  8. Unlocked: turning the service off records nothing. Clear is hidden while locked and works while unlocked.
  9. On Android 15+, step 2's force-stop path behaves the same.

## Review changes

An independent Android review of the first draft (AOSP `ShutdownThread`, `AccessibilityManagerService`, `AccessibilityServiceConnection`, `AccessibilityUserState`; `Intent.ACTION_SHUTDOWN` docs):

| Finding | Change |
|---------|--------|
| High: `ACTION_SHUTDOWN` reaches registered receivers only, since API 28 | Dropped, with the 60 s / 2 min timing rules and the boot fallback |
| High: shutdown/reboot told apart by timing is fragile (slow OTA reboots; user switch unbinds with no shutdown) | A stop counts only if the enabled-services setting no longer lists Stad (written before the unbind) |
| High: the stop write launched on the service scope dies when `onDestroy` cancels it | Synchronous write in `onUnbind`, 2 s timeout, idempotent |
| High: an approximate start from `last_alive` can be days stale | `locked_at` stored with the lock; start = `max(last_alive, locked_at)` |
| Med-High: force-stop then re-enable from Settings without opening Stad went unrecorded | Same-boot `service_connected` marker detects a killed-then-rebound service |
| Med: approximate durations over-count | Approximate entries show "some time after", no firm duration |
| Med: found-off and unlock in one tap | One transition inside `TagRepository.tap`'s edit |
| Med: found-off could beat the exact stop write | An exact start replaces an approximate one |
| Low-Med: the 30 s drop hid real short escapes | Keep user-off periods; drop only sub-5 s toggles; killed restarts need 60 s |
| Low: clocks, work profile, UiAutomation, clearing storage | Clamp and keep order; listed as non-goals |
| Low: wording ("escape", "this week", "force-stopped") | "Blocking history", "last 7 days", "start not known exactly" |
| Low: Play policy doc rows | Device admin row → not used; stored data lists on/off times; Data safety unchanged |
| Tests / plan order | Test list and phone checks expanded; tracker API fixed before Task 1 |
