# Slice 2.1 — Lock survives — Design

**Date:** 2026-11-20
**Branch:** `phase/2-slice1-lock-survives` (cut from `phase/1-slice3-nfc-lock`; rebased onto `main` once 1.3 merges)
**Status:** revised after an independent review (see "Review changes")

## Problem

The lock is already saved in DataStore, so it survives a reboot, an app update or a force-stop on disk. What doesn't survive cleanly is *blocking*:

1. **A blocked app already in front when the service (re)connects isn't blocked.** The service only learns the foreground app from the next window-state event (`lastForeground` starts null). After an app update, a crash restart, or the user re-enabling the service, someone sitting in Instagram stays in it until they switch screens. Instagram is one activity, so that can be indefinitely.
2. **Nobody is told when blocking is off while locked.** A force-stop always disables Stad's Accessibility service (AOSP removes a force-stopped package's services from the enabled list) (and since Android 15 a force-stopped app stays stopped until opened). The lock still says Locked, but nothing is blocked, and Home only shows the generic "Blocking is off" card. A boot or update can also find the service off (e.g. the user turned it off in settings, or the system disabled it after repeated crashes).
3. **No test proves it.** Reboot, update and force-stop behaviour has never been checked.

## Goals

1. After a reboot, an update of Stad, or the service restarting, a locked phone blocks the blocked apps again with no user action, including the one already on screen.
2. When Stad is locked but its Accessibility service is off, the user is told plainly and given a one-tap route to fix it: on Home, and by a notification after boot or update.
3. After a force-stop, the next time the user opens Stad (or taps the tag, which opens Stad), Home walks them through re-enabling blocking.
4. Documented, repeatable phone checks for reboot, update and force-stop.

## Non-goals

- Stopping force-stop, uninstall or disabling the service while locked: slice 2.2.
- Automatically restarting a force-stopped Stad: Android doesn't allow it, by design.
- Direct-boot (before first unlock) blocking: apps can't be opened before first unlock anyway, and DataStore lives in credential-encrypted storage. `TODO(slice2.x-direct-boot)` only if a reason appears.
- Changing the fail-open read rule (a storage read error reads as Unlocked). Kept: a storage fault must never trap the user. The flow retries, so a transient error at boot re-locks once storage reads.

## Behaviour

### What Android already does (verified in the review, not built here)

- Enabled Accessibility services are bound again by the system after boot (once the user unlocks) and after the app is updated; a crashed service stays enabled and is rebound. The service reads the lock from DataStore on connect.
- **Force-stop disables the service, always.** `AccessibilityManagerService.onPackagesForceStoppedLocked` removes the package's services from the enabled list and saves the setting; it does not come back when the process restarts. Only the user can turn it back on (on a sideloaded build, after "Allow restricted settings"). Preventing force-stop while locked is slice 2.2.
- The tag's `TagActivity` is started by an explicit NFC dispatch, which also clears a force-stopped app's stopped state. On Android 15+, leaving the stopped state delivers `BOOT_COMPLETED`.

### 1. Block on connect

The service can't see which app is in front without window-content access: `getWindows()` needs `canRetrieveWindowContent`, which Stad keeps off for Play policy, and `UsageStatsManager` needs a special permission. So when the foreground app is unknown, going Home is the only reliable way to make sure no blocked app stays on screen. Home is never blockable, and whatever the user opens next is evaluated as normal.

Rule, applied at **every lock emission and block-list emission until the foreground is known or Home has been sent once** since connect:

- Locked, block list non-empty, foreground known (a window event arrived before storage was read) → `evaluate(lastForeground)` as usual. No Home.
- Locked, block list non-empty, foreground unknown → `GLOBAL_ACTION_HOME`, once per connect.
- Unlocked, or empty block list → nothing (yet).

Basing it on "foreground unknown" rather than "first lock value" matters: on a storage read error, `retryingOnReadError` first emits empty preferences (reads as Unlocked), and the real `Locked` arrives later. That is most likely at boot. The `justLocked` path alone would see `lastForeground == null` and do nothing.

- Cost: after a Stad update while locked, the app that was open goes to the background once, even an unblocked one (navigation, a call screen comes back from the notification). Acceptable for a commitment app, and rare. Stated in the changelog and in the Play Accessibility declaration ("may return to the home screen when blocking restarts while locked").
- Pure decision in core: `ConnectCheck.decide(lockState, blockListEmpty, foregroundKnown, homeSent) -> GoHome | EvaluateForeground | Nothing`, tested for each case including the error-then-locked sequence.

When the service connects, it also cancels the "blocking is off" notification (section 2): a connected service means blocking works, including when the user re-enabled it straight from Settings.

### 2. Warn when locked but blocking is off

**Home.** When locked and the service is off, the service card changes from the generic "Blocking is off" to a warning in the error colour: "Stad is locked, but blocking is off, so nothing is blocked. Turn Stad's Accessibility service back on." with **Turn on** (the existing disclosure dialog, then Accessibility settings) and the restricted-settings hint. Pure choice in core: `BlockingHealth.of(lockState, serviceEnabled) -> Ok | OffUnlocked | OffWhileLocked`.

**Notification after boot or update.** A `BootReceiver` (manifest: `BOOT_COMPLETED`, `MY_PACKAGE_REPLACED`; `exported="false"`, since both are protected system broadcasts that reach unexported receivers, to be confirmed on the phone; ignores any other action, via a pure `BootCheck.handles(action)`) runs `goAsync()` and, inside `try/finally { finish() }`:

1. reads the lock with `withTimeoutOrNull(5 s) { LockStateRepository(context.stadSettings).lockState.first() }`, using the process-wide `stadSettings` delegate (never a second DataStore for the same file; the service may share the process). A timeout or read error reads as Unlocked, so no warning: the fail-open rule;
2. reads the enabled-services setting;
3. if `BlockingHealth` is `OffWhileLocked` and notifications are enabled (`NotificationManagerCompat.areNotificationsEnabled()`), creates the channel and posts one notification: "Stad is locked, but blocking is off" / "Tap to turn it back on." Tapping opens Home (`FLAG_IMMUTABLE` PendingIntent).

It does nothing else: it doesn't start the service, since Android binds enabled services itself, and can't enable one.

On Android 15+, opening a force-stopped Stad (or tapping the tag) delivers `BOOT_COMPLETED`, so the notification may appear while Home already shows the warning. Accepted: Home cancels it as soon as it's visible (below), so it's brief.

- Channel: "Blocking warnings", default importance. Notification id fixed, so repeats replace rather than stack. Cancelled when the service connects, and by Home whenever it's shown (Home carries the same warning itself).
- **Permission:** `POST_NOTIFICATIONS` (Android 13+). Asked from a Home card "Let Stad warn you if blocking stops" with **Allow** and **Not now**, shown only on 13+ when not granted and not dismissed; dismissal is remembered in DataStore (`notify_prompt_dismissed`). No permission: no notification, Home still warns. Below 13 the permission is granted at install.
- Why not just check on boot and fix it? Re-enabling an Accessibility service needs the user; an app can't do it.

### 3. After a force-stop

The service is disabled (see above) and Stad is stopped, so nothing runs until the user opens Stad or taps the tag. Then Home shows the locked-but-off warning (section 2) and **Turn on** leads to Accessibility settings; once re-enabled, block-on-connect (section 1) covers the app in front. The tag toast already says "Locked, but blocking is off. Open Stad to turn it on." for a lock. This slice only makes the gap visible; closing it (stopping force-stop while locked) is 2.2.

## Acceptance

- CI green: build, unit tests, lint.
- New JVM tests: `ConnectCheck` (unknown foreground → GoHome; known → EvaluateForeground; unlocked or empty list → Nothing; Home already sent → Nothing; Unlocked-then-Locked after a read error → GoHome), `BlockingHealth` (all four combinations), `BootCheck` (the two actions yes, anything else no).
- On David's phone, locked with Instagram blocked:
  1. **Reboot** → unlock the phone → open Instagram → block screen. No notification.
  2. **Update** (run the app again from Android Studio, or `adb install -r` a newer build from the same machine. Two CI APKs can't be installed over each other: each CI run signs with a fresh debug key, so the install is refused. `TODO(slice2.1-ci-debug-key)` if that becomes a nuisance) while Instagram is open → Instagram goes to the background straight away; reopening it is blocked.
  3. **Service off, then reboot:** turn Stad's Accessibility service off in settings while locked, reboot → notification "Stad is locked, but blocking is off" → tap → Home shows the warning → Turn on → blocking resumes.
  4. **Force-stop** (Settings > Apps > Stad > Force stop) → Instagram opens unblocked (expected; fixed in 2.2) → open Stad → Home shows the locked-but-off warning (a brief notification may also appear on Android 15+) → Turn on (allow restricted settings if asked) → Instagram is blocked again.
  5. Unlocked: none of the above shows a warning or sends the user Home.
  6. **Re-enable from Settings directly** after step 3's notification → the notification disappears.

## Review changes

An independent Android review of the first draft (sources: AOSP `AccessibilityManagerService`, Android 15 behaviour changes, `AccessibilityService.getWindows()` and `Intent` references):

| Finding | Change |
|---------|--------|
| High: force-stop always disables the service; it never rebinds on its own | Section 3 and acceptance step 4 say so; only Home's warning helps; prevention stays in 2.2 |
| High: "go Home on the first lock value" misses a read error at boot (first value reads Unlocked, `lastForeground` is null when Locked arrives) | Rule is "foreground unknown", checked on every emission until settled; tested |
| Medium: going Home is blunter than needed | Evaluate the known foreground instead; skip with an empty block list |
| Medium: notification only cancelled by Home | Also cancelled when the service connects |
| Medium: Android 15+ sends `BOOT_COMPLETED` when a stopped app is opened | Documented and accepted; Home cancels it |
| Medium: receiver timing and DataStore | 5 s timeout, shared `stadSettings`, channel + immutable PendingIntent, `finish()` in `finally` |
| Low: receiver needn't be exported | `exported="false"`, confirmed on the phone |
| Low: Play declaration | Mention the return-to-Home behaviour; `06_PLAY_POLICY` lists `POST_NOTIFICATIONS` |
| Low: thin tests | Richer `ConnectCheck`, `BootCheck` in core |
| Open questions | Force-stop: always disabled. `getWindows()`: needs window content, rejected. `adb install -r`: delivers `MY_PACKAGE_REPLACED` (same signing key) |
