# Slice 1.3 — NFC pairing and lock/unlock — Design

**Date:** 2026-11-18
**Branch:** `phase/1-slice3-nfc-lock`
**Status:** draft, revised after an independent review (see "Review changes")

## Problem

Slices 1.1 and 1.2 can block apps, but only a debug button locks and unlocks. Stad's whole idea is that a physical tag is the only way to lock and unlock. This slice adds that: pair one NFC tag; tapping it locks; tapping it again unlocks.

## Goals

1. Pair one tag from Home while unlocked. Pairing can be repeated (replaces the old tag) only while unlocked.
2. Tapping the paired tag **anywhere** (Stad closed, another app open, the block screen showing) toggles the lock, with a vibration and a short confirmation.
3. Tapping any other tag never changes the lock: "That's not your Stad tag."
4. Home shows the lock state, the paired tag, and plain warnings when NFC is off or missing.
5. The debug Lock/Unlock button stays in debug builds only, so slices can still be tested without a tag. Release builds can lock and unlock only with the tag.

## Non-goals

- Sneaky look (2.3), strict-mode escape routes (2.x), onboarding (3.1).
- More than one paired tag (e.g. a spare). Possible later: `TODO(slice3.x-spare-tag)`.
- Unpairing while locked, or any lost-tag bypass. By design (03_PRODUCT_DESIGN "Lost tag").
- Protection against a cloned tag. A determined user can copy a UID; Stad is a commitment device, not a security product. Stated in docs.

## User flow

1. **Home, unlocked, no tag:** "No tag paired." **Pair a tag** → pairing sheet: "Hold your tag to the back of the phone." → success: "Tag paired." (+ vibration). Pairing takes two taps: the first reads the UID and writes the Stad record, the second confirms the same UID and checks the record reads back. Errors: "Couldn't write to this tag, try again" / "This tag can't be written. Use another tag." / "This tag changes its ID each time, so Stad can't use it."
2. **Lock:** tap the paired tag anywhere → vibration + "Locked · 6 apps blocked". If the blocking service is off: "Locked, but blocking is off. Turn it on in Stad." If the list is empty: "Locked · no apps chosen".
3. **Locked:** opening a blocked app shows the block screen ("Tap your tag to unlock." in release builds). Pair/re-pair is disabled, the picker is read-only. Tapping to lock while a blocked app is open blocks it at once.
4. **Unlock:** tap the same tag → vibration + "Unlocked". If the block screen is showing, it closes itself.
5. **Other tag:** "That's not your Stad tag." (short vibration pattern), nothing changes.
6. **NFC off:** Home card "NFC is off. Stad needs NFC to read your tag." **Turn on** → `Settings.ACTION_NFC_SETTINGS` (fallback: wireless settings, then a message). **No NFC hardware:** "This phone can't read NFC tags, so Stad can't lock." Pairing is hidden.

## Design

### Tag identity and the Stad record

- **Identity is the tag UID** (`Tag.id`), stored as uppercase hex without separators. Reading the UID needs no writing and works on any tag type the phone can see.
- **Launch from anywhere** needs an NDEF record, because Android only dispatches `NDEF_DISCOVERED` reliably to a matching filter. Pairing writes one NDEF message, in this order (dispatch matches the **first** record; the AAR only picks the package):
  1. URI record `https://stadapp.cc/t`, and
  2. an Android Application Record (AAR) for `cc.stadapp.stad`, so Android starts Stad's matching activity directly. If Stad isn't installed, Android opens its Play Store listing (or, on phones with no store, the website, which explains what the tag is).
- The `TagActivity` filter must match exactly, or Android falls back to launching `MainActivity` with no tag: `NDEF_DISCOVERED` + `category.DEFAULT` + `<data scheme="https" host="stadapp.cc" path="/t"/>`.
- The record holds no secret and no UID. It only routes the tap; the UID decides.
- Supported tags: NDEF-formattable NFC Forum Type 2 (NTAG213/215/216). Blank tags are formatted (`NdefFormatable`); NDEF tags are overwritten (`Ndef.writeNdefMessage`) after checking `isWritable` and `maxSize`. All tag I/O runs on the reader-mode callback thread, never the main thread. MIFARE Classic is not supported on many phones and isn't targeted.
- **Unwritable tag:** refused ("Use another tag"). A tag with no record would only work while Stad is open; that mode is cut from this slice. `TODO(slice3.x-readonly-tag)`.
- **Tag pulled away mid-write:** NTAG writes page by page, so a partial write can corrupt the record. The second pairing tap re-reads the NDEF message and rewrites it if the URI or AAR is missing; pairing only succeeds once the record reads back intact.
- **Random UIDs:** some cards (and phones emulating cards) present a new random UID each tap. A 4-byte NFC-A UID starting `0x08` (the ISO 14443-3 random-ID marker) is refused on the first tap; the two-tap match is the backstop.

### core/ (pure Kotlin, JVM-tested)

- `TagId`: `fromBytes(ByteArray)` → hex string; `normalize(String?)` (trim, uppercase, strip `:`/spaces; blank → null); never logs.
- `TagAction.decide(scannedId, pairedId, lockState) -> TagOutcome`:
  - `NotPaired` when no tag is paired (scan ignored outside the pairing sheet).
  - `NotYourTag` when it doesn't match.
  - `Lock` / `Unlock` from the current state when it matches.
  - `NotPaired` never locks (test).
- `StadTagUri`: the constant `https://stadapp.cc/t` and `matches(uri: String?)`: exact match (case-insensitive scheme and host), the same as the manifest filter, since Stad writes the record itself.
- `PairingCheck`: `isRandomUid(bytes)` (4 bytes, first `0x08`) and `confirm(firstId, secondId)`: same non-blank ID twice → `Confirmed(id)`, else `Unstable` / `Missing`.
- `TagFeedback.of(outcome, blockedCount, serviceOn, writeFailed)` → message + haptic pattern (Locked · N apps blocked / Locked, but blocking is off / Locked · no apps chosen / Unlocked / That's not your Stad tag / Couldn't change the lock).
- `TapDebounce`: the same UID within 1.5 s is ignored. Held in a process-wide object, because each tap is a new activity instance.

### data/

- `StadKeys.PAIRED_TAG` (string). `TagRepository`:
  - `pairedTag: Flow<String?>` (retrying on read errors like the others; a read error gives null → nothing can toggle, which fails toward "unchanged", never toward locking).
  - `pair(id)`: inside one `edit`, refuses while `lock_state` is Locked (same pattern as the block list), else stores the ID.
  - `tap(scannedId): TagOutcome`: **one `edit`** reads `paired_tag` and `lock_state`, runs `TagAction.decide`, writes the new lock state for `Lock`/`Unlock`, and returns the outcome. Two taps can't interleave and a re-pair can't race a toggle.
- Lock-state readers are unchanged (1.2's `LockStateRepository` / service).

### service/ and NFC entry points

- **`TagActivity`** (new, `exported="true"`, `Theme.Translucent.NoTitleBar` with no `screenOrientation` (a translucent activity that sets one crashes on API 26), `excludeFromRecents`, `taskAffinity=""`, `launchMode="standard"`): the filter above. On create: acts only if `action == NDEF_DISCOVERED` and `EXTRA_NDEF_MESSAGES` contains the Stad URI; takes the UID from `EXTRA_TAG`'s `tag.id` (never `EXTRA_ID`); debounces; calls `TagRepository.tap` in an **app-scoped** coroutine (so finishing the activity, or the block screen appearing, can't cancel the write); vibrates and shows the toast **while still in the foreground** (Android drops vibrations from background apps); then `finish()`. Translucent rather than `NoDisplay`, because `NoDisplay` must finish before `onResume` and the write is async.
  - **Forged taps:** `Tag` is a public Parcelable, so another app can build one with any UID and send it to `TagActivity`; the sender can't be checked. Forging still needs the paired UID, which only Stad's private storage and the physical tag hold. That's the same capability as cloning the tag, which is already accepted.
- **`MainActivity` reader mode** (`NfcAdapter.enableReaderMode`, NFC-A | B | F | V so bank and transit cards are seen too) while resumed: in the pairing sheet a tap goes to pairing; otherwise it goes to `TagRepository.tap` (so a tag works with Stad open even if it has no record). Reader mode also stops the system dispatching the same tap to `TagActivity` while Stad is open.
- **Feedback:** `Vibrator` / `VibratorManager` one-shot (lock: one 80 ms pulse, unlock: two, not-your-tag: three short). Needs the normal `VIBRATE` permission.
- **Locking over a blocked app:** the 1.2 service re-checks its last app when the lock flips to Locked. `TagActivity`'s own window would otherwise become that "last app" (it's a real activity of Stad), so the service **ignores `TagActivity` events** and doesn't update its last app for them. Then locking over Instagram blocks Instagram at once.
- **Unlocking over the block screen:** `BlockedActivity` collects the lock state and finishes itself on Unlocked.

### ui/

- Home: lock-state card (Locked/Unlocked with the count of blocked apps), tag card (Paired / not paired / works-only-with-Stad-open; **Pair a tag** or **Re-pair**, disabled while locked), NFC card (off / missing), service card (1.2).
- Pairing sheet (bottom sheet): instruction, "Tap again to confirm" after the first read, progress while writing, success/errors as above. Cancel closes it.
- Block screen message: release "Tap your tag to unlock." Debug: "Tap your tag, or open Stad and tap Unlock (debug)." (replaces the 1.2 debug text).
- Debug Lock/Unlock button stays under `BuildConfig.DEBUG`. `TODO(slice1.3-remove-debug-toggle)` is resolved by this: release never had it; the TODO is removed and the code comment says it's debug-only by design.

### Manifest

- `<uses-permission android:name="android.permission.NFC" />`, `VIBRATE`.
- `<uses-feature android:name="android.hardware.nfc" android:required="true" />` so Play only offers Stad to phones with NFC. (Sideloaded debug installs ignore it; Home still handles "no NFC".)
- `TagActivity` declaration and filter as above.

## Play policy

- `NFC` and `VIBRATE` are normal permissions; no declaration needed.
- Stored data gains the paired tag's UID (already listed in `06_PLAY_POLICY.md`). Nothing leaves the device.
- The Accessibility disclosure is unchanged.

## Edge cases

- **Tap while the phone is locked (keyguard):** Android doesn't read NFC tags with the screen off and, by default, not on the lock screen. Unlock the phone first. Documented, not worked around.
- **Tap during a phone call or another NFC app in front:** the foreground app's reader mode wins; open Stad and tap again.
- **Another app also claims `https://stadapp.cc/t`:** the AAR makes Android launch Stad regardless. Without Stad installed, Android opens the Play Store listing, or the website on phones with no store. `stadapp.cc/t` should exist and explain the tag.
- **Lock-screen taps on some phones:** AOSP reads tags only when the phone is unlocked. Some makers also read on the lock screen; there the lock still toggles, but the confirmation may not be seen.
- **Debug APK:** the CI debug build keeps the Lock/Unlock button. It can't install over a store build (different signature), so it isn't a bypass for store users.
- **Re-pair:** only while unlocked; the old tag stops working at once. The old tag still carries the Stad record, so tapping it launches Stad, which says "That's not your Stad tag."
- **Tag lost while locked:** no bypass (by design). Recovery: turn off Stad's Accessibility service in system settings (still possible until 2.2). Home says this in the tag card's help text.
- **Storage write fails during a tap:** nothing changes; toast "Couldn't change the lock, try again." The lock never changes without a confirmed write.
- **Double tap (tag held near the phone):** each NFC discovery is one toggle. Android re-dispatches only after the tag leaves the field, so holding it doesn't flap. `TapDebounce` (1.5 s, same UID) covers flaky readers in both `TagActivity` and reader mode.

## Acceptance

- CI green: build, unit tests, lint.
- New JVM tests: `TagId` (bytes → hex, normalize), `TagAction.decide` (all outcomes; `NotPaired` never locks), `StadTagUri.matches`, `PairingCheck` (random-UID rule, confirm), `TagFeedback`, `TapDebounce`, `TagRepository` (pair, refuse pair while locked, tap toggles, wrong tag and not-paired leave state unchanged, `tap` and `pair` serialise, a write error leaves the lock unchanged).
- On David's phone with an NTAG215: pair (two taps); close Stad; tap → locked + vibration; Instagram blocked; tap → unlocked; another tag or a bank card → "not your tag"; re-pair disabled while locked; NFC off → Home card; **tap to lock while Instagram is open → blocked at once**; tap to unlock while the block screen shows → it closes.
- `adb shell am start -a android.nfc.action.NDEF_DISCOVERED -d https://stadapp.cc/t` resolves to `TagActivity` (not `MainActivity`) and does nothing without a tag.

## Review changes

An independent Android review of the first draft:

| Finding | Change |
|---------|--------|
| High: `TagActivity` would become the service's "last app", so locking over a blocked app wouldn't block it | Service ignores `TagActivity` events |
| High: filter without `category.DEFAULT` falls back to `MainActivity` with no tag | Exact filter spelled out; URI record first; `StadTagUri` matches exactly |
| High: the write could be cancelled when the activity finishes or the block screen appears; background vibration is dropped | App-scoped write; feedback while foreground; no `noHistory` |
| Medium: `Tag` can be forged by any app | Stated why it's accepted (needs the UID = cloning); act only on `NDEF_DISCOVERED` with the Stad URI; use `tag.id` |
| Medium: `singleInstance` mishandles a second tap | `standard` launch mode, own task, translucent theme without orientation |
| Medium: tag pulled away mid-write | Second pairing tap verifies the record and rewrites if needed |
| Medium: reader mode only saw NFC-A | A, B, F and V |
| Medium: feedback choice was untested UI logic; debounce state per activity | `TagFeedback` in core; process-wide `TapDebounce` |
| Medium: "not installed opens the browser" was wrong | Opens the Play Store listing; website as fallback |
| Low: random UIDs, lock-screen taps, block screen on unlock, debug APK | `0x08` UID rule; documented; block screen closes on unlock; documented |
| Scope: read-only "pair anyway" mode | Cut; unwritable tags are refused (`TODO(slice3.x-readonly-tag)`) |
