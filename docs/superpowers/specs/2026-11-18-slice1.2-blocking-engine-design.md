# Slice 1.2 — Blocking engine — Design

**Date:** 2026-11-18
**Branch:** `phase/1-slice2-blocking-engine` (stacked on 1.1, PR #2)
**Status:** built (PR #3); revised after an independent plan review (see "Review changes")

## Problem

Slice 1.1 lets you choose apps, but nothing stops you opening them. This slice adds the part that does: an Accessibility service that notices when a blocked app comes to the front while Stad is locked, and covers it with a block screen. NFC tags arrive in 1.3, so a **debug-only Lock / Unlock button** drives the lock for now.

## Goals

1. While locked, opening a blocked app shows Stad's block screen instead; everything else works normally.
2. While unlocked, nothing is blocked.
3. The lock state is shared by the app and the service, through the same DataStore as the block list.
4. Home tells you plainly when the Accessibility service is off, with a button to the right settings screen and a short disclosure first.
5. The 1.1 rule "the block list is read-only while locked" switches on.

## Non-goals

- NFC (1.3). The debug toggle is the only way to lock in this slice.
- Surviving reboot / force-stop / update and the boot receiver (2.1). The lock state is stored, so it survives Stad being closed, but 2.1 owns the guarantees and tests for those escape routes.
- Blocking uninstall, Accessibility settings or App info while locked (2.2).
- Sneaky look (2.3), full onboarding and the final disclosure wording (3.1).

## User flow

1. Home (service off): "Blocking is off. Stad needs its Accessibility service to block apps." **Turn on** → disclosure dialog (what Stad reads, why, nothing stored or sent) → **Open settings** → system Accessibility settings. Stad never turns the service on itself.
2. Home (service on, debug build): **Lock now (debug)** / **Unlock (debug)** button. Release builds don't have it.
3. Locked: open Instagram → the block screen appears: "Instagram is blocked by Stad. Tap your tag to unlock." with **Go to home screen**. Back also goes home.
4. Unlocked: Instagram opens normally.
5. Picker while locked: read-only with the 1.1 banner.

## Design

### core/ (pure Kotlin, JVM-tested)

- `BlockDecision.decide(foregroundPackage, lockState, blockList, protection) -> Decision` (`Allow` or `Block(packageName)`).
  - `Allow` when unlocked, when the package is blank, Stad itself, protected, or not in the list.
  - Protection uses the last **complete** protected set. If there has never been one, it allows everything (better to miss a block than to block a launcher and trap the user); this fail-open choice is deliberate.
- `RelaunchGuard`: don't start the block screen again for the same package within 500 ms unless a different, allowed package was seen in between. Stops loops without stopping a real re-block a second later.
- `AccessibilityStatus.isEnabled(enabledServicesSetting, stadComponent)`: parses `ENABLED_ACCESSIBILITY_SERVICES` by component, so the short (`pkg/.Cls`) and full forms both match.
- Protected floor grows: `com.android.phone` (the emergency dialer is separate from the default dialer) and known emergency/safety apps (`com.android.emergency`, `com.google.android.apps.safetyhub`, Samsung's SOS app).

### data/

- `LockStateRepository` on the same `stad_settings` DataStore, key `lock_state` (enum name; missing or unknown → `Unlocked`). A read error also gives `Unlocked`: failing open is deliberate, so a storage fault can never trap the user.
- **Lock check inside the write.** Block-list edits read `lock_state` from the same preferences inside the same `edit {}` and refuse while locked, so an edit can't land just after a lock. The ViewModel's in-memory lock from 1.1 is replaced by this flow.

### service/

- `BlockerAccessibilityService`
  - Config: `typeWindowStateChanged` only, `feedbackGeneric`, `notificationTimeout` 100 ms, `canRetrieveWindowContent="false"`, a plain description, no `isAccessibilityTool`. (`TYPE_WINDOWS_CHANGED` would need window content; refused.)
  - On connect it collects the lock state and block list into memory.
  - Each event: only events whose class is an **Activity** of that package count (`getActivityInfo`; listed apps are visible through the LAUNCHER `<queries>`). Dialogs, popups and chat-head overlays from a blocked app don't send you home while you're in another app.
  - On `Block`: recompute the protected set right then (cheap, and blocks are rare, so a changed default launcher/dialer/SMS/keyboard is never stale), re-decide, then `performGlobalAction(GLOBAL_ACTION_HOME)` and start `BlockedActivity` with `NEW_TASK | CLEAR_TASK`. Going home first means the app is off-screen even if the start is slow or refused.
  - The last foreground package is kept **in memory only**. When the lock flips to `Locked`, it's re-checked, so locking while a blocked app is open blocks it at once (matters for 1.3 tag taps).
  - Package names are never persisted or logged.
- `BlockedActivity`: `exported="false"`, `excludeFromRecents`, own task affinity, `singleTask`; `finish()` in `onStop` so a stale block screen never comes back (e.g. after unlocking). App name and icon, message, **Go to home screen**; Back goes home. TalkBack-readable.
- `ProtectedPackages` gains **every enabled keyboard** (`InputMethodManager.enabledInputMethodList`), not just the default, and the emergency floor above.

### ui/

- Home: service status card. Off → disclosure dialog → system Accessibility settings. The card also says: "If the switch is greyed out: App info → ⋮ → Allow restricted settings" (Android 13+ blocks it for sideloaded apps).
- Home shows a warning when protected apps couldn't be confirmed. The ViewModel already runs `ProtectedPackages.current()`, so the UI uses its own result rather than reading the service's.
- Debug builds: Lock/Unlock button (`BuildConfig.DEBUG`; `buildConfig = true`). `TODO(slice1.3-remove-debug-toggle)`.
- Picker: read-only while locked (1.1 banner).

### Background starts

Starting an activity from a service normally hits Android's background-activity-start limits. An Accessibility service bound by the system is exempt, which is why the block screen is started from the service. To verify on a real phone (Android 14+) in the acceptance test.

## Play policy

This slice turns on the Accessibility use, so `06_PLAY_POLICY.md` must stay true:
- Service subscribes to window-state changes only; no window content.
- Reads only the foreground package name and its activity class; keeps the last one in memory only; never persists, logs or sends it.
- **The disclosure is Play-compliant from this slice**, because any closed-test build before 3.1 would be reviewed with it: shown in the normal flow before settings, says what is accessed and why, explicit **Agree** button, and dismissing it is not consent. 3.1 polishes it into onboarding.

## Edge cases

- **Blocked app already open when you lock:** blocked the next time it raises a window event (switching back to it). Stad doesn't kill running apps.
- **Overlays:** chat heads and popups from a blocked app aren't blocked (Activity-only check); the full app is.
- **VoIP apps:** a blocked VoIP app's incoming-call screen is blocked too. Don't block apps you need to receive calls on.
- **Split screen / picture-in-picture:** a blocked app in PiP or split screen is blocked when it takes focus. Full coverage of multi-window is out of scope. `TODO(slice2.2-multiwindow)`.
- **Notification shade, keyboard, system dialogs:** protected or not in the list, so ignored.
- **Service killed by the system:** Android restarts enabled Accessibility services; state comes from DataStore on reconnect.
- **Work profile:** blocking is by package name, so a work-profile copy of a blocked app is blocked too (noted in 1.1).

## Acceptance

- CI green: build, unit tests, lint.
- New JVM tests: `BlockDecision` (unlocked, locked + listed, locked + unlisted, protected, Stad itself, blank, keyboard, never-complete protection), `RelaunchGuard`, `AccessibilityStatus` parsing (short and full forms, other services, empty), `LockStateRepository` (default, set, unknown → Unlocked), and a repository test that a list edit while locked leaves the stored list unchanged.
- On David's phone (debug APK): turn on the service via Home; pick Instagram; **Lock now**; open Instagram → block screen; Go to home screen works; Phone, Messages and the launcher still open; **Unlock** → Instagram opens. Close Stad from recents while locked → Instagram still blocked.

## Review changes

An independent Android review of the first draft:

| Finding | Change |
|---------|--------|
| "Ignore while the block screen is up" can't be seen by the service and would stop real re-blocks | Pure `RelaunchGuard`; go Home first, then `NEW_TASK \| CLEAR_TASK`; block screen not exported and finishes in `onStop` |
| Protected set stale after changing default launcher/dialer/SMS/keyboard | Recomputed on every `Block` decision |
| Lock check not atomic with list writes | Read `lock_state` inside the same DataStore `edit` |
| Home couldn't see the service's protection state | UI uses the ViewModel's own `ProtectedPackages` result |
| Overlays and popups would block allowed apps | Only Activity windows of the package count |
| Emergency apps dropped | `com.android.phone` + known emergency/safety apps in the floor |
| "Enabled" parsing and restricted settings | Component-based parsing in core; greyed-out-switch hint |
| Interim disclosure may be what Play reviews | Make it compliant now |
| Locking with a blocked app open | Re-check the in-memory last package on lock |
| Low: only the default keyboard, fail-open undocumented, docs say lock persists in 2.1 | All enabled keyboards; fail-open documented; docs updated |
